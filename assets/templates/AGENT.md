## 2. 绝对约束

违反任一条，宁可停下并报告，不要"试试看"。

| # | 约束 | 原因 |
|---|---|---|
| 1 | 不得修改 `{{SOURCE_ROOT}}` 源工程 | 它是唯一可信的原始快照；产物写 `work/` 或新目录 |
| 2 | 不得分发原版镜像与未修改的游戏资源 | 版权；仓库只含脚本、文档、译文与改动过的补丁负载 |
| 3 | 不得改文本表的 `jp` 字段 | ID 由源字节哈希生成，改原文会让所有批次失联 |
| 4 | 不得重排已分配的 glyph 别名 | 旧译文按旧别名编码；重排必须整体重编码全部译文 |
| 5 | 不得用一套字库假设处理另一套 | 正文/诗文/ruby 的网格、每页字数、上限各不相同 |
| 6 | 不得跳过未修改回环校验 | 否则无法证明"只改了目标像素/字节" |
| 7 | 不得把检索命中当已确认错误 | 会产生批量新错误 |
| 8 | 不得把未读内容标记为已审 | 进度必须真实 |
| 9 | 不得在没有报告的情况下构建 | 无哈希/计数的产物不可追溯 |
| 10 | 不得重建规格未验证的结构（如 ETOC） | 只能原样搬运已知字段 |

## 4. 标准作业流程

### 4.0 首次接管

```sh
python3 <skill>/scripts/hh.py doctor        # 看缺什么
python3 <skill>/scripts/hh.py text check    # 文本结构
python3 <skill>/scripts/hh.py verify . --overlay data/overlay   # 变更集
```

不要跳过体检直接跑构建；也不要手工往 `work/` 里塞文件——它随时可以被删掉重建。

### 4.1 接任务

先判断属于哪一层：

| 层 | 典型任务 | 先读 |
|---|---|---|
| 文本 | 改译、修人称、补漏句 | `references/02-text-layout.md` |
| 排版 | 换行、溢出 | `references/02-text-layout.md` |
| 字库 | 缺字、方块、字数上限 | `references/03-font.md` |
| 诗文 / ruby | 碎字、双层结构 | `references/03-font.md` |
| UI 图片 | 日文残留、花屏 | `references/04-images-ui.md` |
| 构建 / 写回 | 黑屏、读不到 | `references/platforms/<平台>.md` |
| 质量 | 语义校对、验收 | `references/05-quality.md` |

> **平台先查状态**：`references/platforms/README.md`。若本平台是 **S0 占位**，说明没有验证过的
> 平台流程——构建/写回只能按 `01-pipeline.md` 的通用阶段现场取证，证据写进 `data/evidence/`，
> 并标证据类型。**不要拿 PSP 的容器与参数套用。**

### 4.2 复现

- 找到最小输入（一个文件、一个 ID、一个矩形）；
- 写/跑一个只依赖该输入的检查；
- 记录哈希与现象；
- 确认问题可重复，再改。

### 4.3 变更

- 一次只改一类；
- 修改前备份（`*.pre-<reason>.jsonl`）；
- 配置与代码分离；
- 失败要早：输入哈希、旧字节、矩形溢出、映射缺失，任一不符即中止。

### 4.4 验证

至少跑：

```sh
python3 <skill>/scripts/hh.py text check     # L1：控制码 / ruby / id
python3 <skill>/scripts/hh.py glyphs         # 字符集与容量
python3 <skill>/scripts/hh.py overlay <原树> <改后树> --dry-run   # 变更面是否合理
```

再加：

- 变更资源的回环；
- 抽检 20 条读回；
- 更新报告与哈希。

### 4.5 汇报

必须包含：

1. 改了什么（文件、数量）；
2. 证据（命令输出、哈希、报告路径）；
3. 验证到哪一层（结构 / 语义 / 运行时）；
4. 未完成 / 风险；
5. 下一步建议。

不要只写"已完成"。

## 5. 翻译规范

### 5.1 必须

- 先读上下文（按 `file + text_offset` 排序，不按 ID）；
- 保留控制码与占位符（`#C...`、`#SVT[...]`、`#RUBS/#RUBE/#REND`、`\n`、`{0}`、`[var]`、`<color>`）；
- 保留分支与称谓差异；
- 术语以 `data/translation/glossary.csv` 为准；
- 遵守行宽上限（见 `project.json` 的 `gates.max_line_width`）；
- 修正写 `id / zh_cn / reason`，不直接改主表。

### 5.2 禁止

- 把 `しか…ない` 译成肯定；
- 把 `じゃないか` 译成否定陈述；
- 把普通日文读音硬贴到中文正文；
- 把 ruby 两层译成同一个词；
- 为"通顺"删掉颜色/分支/控件码；
- 编造原文没有的机制、数字、专名。

## 6. 代码规范

- Python 3.9+，优先标准库；图像处理用 Pillow/numpy。
- CLI 用 `argparse`，每个参数有 `help`。
- 路径用 `pathlib`，默认值相对工程根。
- 读写二进制显式 `"rb"/"wb"`。
- 不用裸 `except`；错误信息带文件/偏移/ID。
- 不静默回退：映射缺失、哈希不符、长度异常都抛错。
- 大文件用流式/分块，不一次性读 1GB 镜像到内存。
- 输出报告用 JSON，字段稳定、可机器读。
- 新增脚本在 `scripts/README.md` 登记用途、输入、输出。

### 6.1 命名

- 生产脚本：`<动作>_<对象>.py`
- 审计脚本：`<动作>-<对象>.py`
- 报告：`<对象>-<类型>.json`
- 快照：`text.pre-<原因>.jsonl`

### 6.2 提交信息

```
<area>: <what changed>

Why: <root cause / requirement>
Verify: <command + result>
```

`area` 取值：`text`、`font`、`image`、`build`、`docs`、`tooling`。

## 7. 验证门槛

按变更类型选门槛，未过不提交：

| 变更 | 最低验证 |
|---|---|
| 文本 | 可编码 0 失败；控制码一致；抽检 20 条 |
| 排版 | 行宽分布；动画/逐字文本未被插入换行 |
| 字库 | 上限内；映射唯一；图集非空；回环 |
| 文本 + 字库 | 字符集全覆盖；旧别名未重排 |
| 图片 | 未修改回环；矩形不溢出；别名包全分发 |
| 构建 | 条目数一致；容器可自解析；启动 |
| 文档 | 数字与报告一致；无"全部完成"式表述 |

## 9. 遇到不确定时

按顺序：

1. 查 `docs/` 与审计报告；
2. 用真实字节做最小实验；
3. 能反汇编就反汇编，给出地址与指令；
4. 仍不确定 → 在报告中标记"未验证"，不要写成结论；
5. 影响面大（可执行文件、容器索引、卷结构）→ 停下，向人类确认。

## 10. 禁止的捷径

- "先全量替换再看哪里崩" —— 无法定位；
- "字数不够就覆盖日文字位" —— 未提取的 UI 会错字；
- "看起来对就行，不用回环" —— 会悄悄改坏其他像素；
- "用 OCR 结果直接当译文" —— 小字/描边必错；
- "批量勾选已审" —— 质量数据失真；
- "把一种网格套到所有字库" —— 碎字的根因；
- "发布说明写完美汉化" —— 与实际范围不符。

---

## 11. 一句话

> 先证明，再修改；一次一类；每步留证；不确定就说不确定。
