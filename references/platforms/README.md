# 平台索引：按主机区分，不按引擎区分

汉化流程的组织维度是**主机平台**，因为决定"能不能拆、怎么拆、怎么装回去"的是
硬件载体的约束（镜像结构、容器、内存上限、字库形态），不是游戏用了什么引擎。

**引擎/中间件只作为平台文档内部的一个字段记录**（例如 PSP 案例里的 CRI CPK），
不单独开专题——同一个引擎在不同主机上的产物结构也不同，按引擎写会写出一堆没验证过的通论。

---

## 1. 验证状态（与 `00-discipline.md` 的证据类型 E1–E5 是两套刻度，别混用）

| 状态 | 含义 |
|---|---|
| S0 stub | 无任何实测，只有占位问题清单 |
| S1 单点 | 单点改动被观察到（改一处，游戏内可见变化） |
| S2 可解析 | 结构可解析（容器/指令/字库能被自己的解析器完整读出） |
| S3 可复现 | 参数在第二个样本上仍成立 |
| S4 可交付 | 有可运行产物 + 变更集 + 分层验收记录 |

平台文档必须自报状态。**S0 的文档不得包含流程步骤与参数。**
"这个结论有多硬"用 `00-discipline.md` 的 E1–E5 标注；"这个平台摸到哪一步"用这里的 S0–S4。

## 3. 使用规则

1. 接新项目先查本表：
   - 目标是 PSP → 读 `psp.md`，但**仍需按 S0–S2 重新识别**（同平台不同游戏，容器组合与操作码可以完全不同）。
   - 目标是其他平台 → 文档是 stub。此时只能执行 `01-pipeline.md` 的通用阶段，平台细节全部**现场取证**，
     并在项目内记录证据类型（E1–E5）。**不许拿 PSP 的参数顶替。**
2. 项目做通了，再把结论回填到对应平台文档，并把状态从 S0 往上推。回填时附证据文件路径，不写"经验上"。
3. 平台文档只写"这个主机上验证过的做法"；跨平台通用纪律写在 `00-discipline.md` / `01-pipeline.md`。
